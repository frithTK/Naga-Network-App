# Ускорение проверки серверов: реализация и проверка

Дата: 2026-10-14. Исходная версия: 1.2.6; подготовленная сборка: 1.2.7+12.
План: [LATENCY_FIX_PLAN.md](LATENCY_FIX_PLAN.md). Исследование: [KARING_LATENCY_REVIEW.md](KARING_LATENCY_REVIEW.md).

## Изменение поведения

Готовые пинги отображаются во время проверки остальных серверов. Проверка работает как одно фоновое задание control; Flutter опрашивает изменения каждые 300 мс, показывает прогресс и позволяет отменить задание. Последний пинг содержит время замера. Отмена и отсутствие подходящего движка не превращаются в ошибку доступности узла.

Подготовка обычных протоколов, AWG и olcRTC выполняется независимо. Временные движки используют собственные каталоги и порты; их остановка не закрывает работающий VPN. При Start, Stop, восстановлении VPN, переключении движка или изменении профилей задание отменяется и устаревшие результаты перестают применяться.

Для проверки при выключенном VPN убраны TUN, входящие порты, маршрутизация пользовательского трафика и автоматические urltest-запросы. DNS-серверы, цепочки detour, DNS-правила и наборы правил, на которые эти DNS-правила ссылаются, сохранены. Ненужные наборы правил не загружаются. Проверка настоящим sing-box выявила повторное добавление DNS-порта 53 общим кодом запуска; отдельный режим StartProbe исправляет это.

Android-обёртка сохраняет ProbeOnce. Ручная проверка использует один запрос Clash delay; startup/health сохраняют свой контракт. Ядро может делать внутренний прогрев multiplex — один запрос API не гарантирует ровно один сетевой запрос внутри движка. Общая цель измерения — `https://www.gstatic.com/generate_204`; olcRTC при ручном замере выполняет один HEAD через свой SOCKS-транспорт.

## API и ограничения

| Запрос | Результат |
|---|---|
| `POST /v1/nodes/probe/start` | 202 и снимок нового задания; 409 с существующим заданием при повторном запуске |
| `GET /v1/nodes/probe/jobs/active` | Активное задание или null |
| `GET /v1/nodes/probe/jobs/{id}?after_revision=N` | Изменившиеся строки, состояние, ревизия и полные счётчики |
| `POST /v1/nodes/probe/jobs/{id}/cancel` | Идемпотентная отмена |
| `POST /v1/nodes/probe` | Прежний blocking endpoint и JSON списка, поверх того же механизма |

Capability `node_probe_jobs` находится в health. Все новые endpoints используют прежнюю авторизацию до изменения состояния. В POST start можно передать `{"concurrency":16}` для одного стендового прогона. Отсутствующее/нулевое значение сохраняет default; отрицательное значение, превышение платформенного предела и неверные поля возвращают 400. Снимок содержит выбранные пределы и elapsed_ms, посчитанный монотонными часами control. Неверная будущая ревизия возвращает 400 с `full_snapshot_required`; клиент перечитывает снимок, сохраняя идентификатор задания. Неизвестное/истёкшее задание возвращает 404. Ошибка авторизации или JSON не включает fallback на legacy; старый control выбирается по capability.

Общий deadline работы — 180 секунд, включая подготовку всех движков. Таймаут одного обычного узла — 8 секунд, QUIC — 12 секунд; parent deadline ограничивает оба. Опрос клиента состоит из коротких запросов вместо ожидания одного POST на 200 секунд.

Для очистки выделен отдельный grace 5 секунд. Если остановка ресурса не вернулась, задание сообщает failed с `cleanup_complete=false`, остаётся зарегистрированным и запрещает новую проверку/Start. API прогресса и остановка основного VPN доступны. После фактического закрытия ресурса выставляются cleanup_complete и finished_at; повторный запуск разрешается. Ошибка очистки сохраняется в истории. Этот случай проверен управляемым зависшим Stop.

Пул обычных запросов сохраняет default 8; настраиваемый предел ограничен 20 на ПК и 10 на мобильной платформе. Очередь чередует профили. Подготовка AWG и olcRTC ограничена одним временным экземпляром каждого транспорта. Предельный размер задания — 10 000 узлов и 8 МиБ строковых metadata; хранится одно активное и одно последнее завершённое задание, TTL последнего — 5 минут.

Идентификаторы и ключи кеша olcRTC имеют отдельное пространство имён: одинаковое название VLESS и olcRTC в одной подписке больше не объединяет строки и замеры. Контроль применимости результатов использует поколение задания, ревизию профиля и внутренний отпечаток конфигурации. Отпечатки конфигурации не публикуются в API. Узлы изменённой подписки, ещё не загруженные в live runtime, пропускаются с причиной runtime_requires_reload.

## Проверки

Автоматические регрессии проверяют:

- полные задания на 1/10/50/100 узлов с 0/10/50/100% искусственных ошибок при включённом и выключенном VPN; отдельные задания на 1000 узлов;

- готовый ответ при заблокированном медленном узле, delta и согласованность счётчиков;
- повторный Start, Cancel, Probe–Start, право собственности на live/idle runtime;
- отмену подготовки AWG и общий deadline подготовки;
- зависшую очистку, доступность Stop и запрет замещения до освобождения ресурсов;
- авторизацию, неправильные ревизии, TTL, legacy и совместимость старого control;
- один цикл polling, паузу при уходе с экрана/в background, восстановление, ошибку progress и 404;
- защиту от устаревшего замера, смены конфигурации и одинаковых названий разных движков;
- изоляцию портов/YAML olcRTC, readiness после выхода процесса;
- настоящий запуск sing-box без TUN/DNS-inbound, сохранность конфигурации VPN, удаление временных каталогов и повторные циклы без роста FD/горутин сверх допуска.

В widget test готовый пинг виден после 300 мс опроса, пока второй узел ещё проверяется. Это проверка передачи готового результата, а не обещание соединения с удалённым сервером за 300 мс.

Контрольный тест пула с искусственной задержкой 1 мс дал:

| Узлы | Пул 8 | Пул 16 | Пул 20 |
|---:|---:|---:|---:|
| 100 | 17 мс | 10 мс | 8 мс |
| 1000 | 161 мс | 86 мс | 70 мс |

Это локальный синтетический тест с race detector. Он измеряет очередь запросов; запуск движков, сеть, CPU/память телефона и выдача всего JSON в него не входят. Default остаётся 8 до стендового сравнения.

## Сборка Linux

Подготовлен один файл `dist/NagaNetwork-1.2.7-x86_64.AppImage`: UI, naga-control, sing-box, olcRTC и hev внутри. Размер 42 064 376 байт; SHA-256:

`d034ba2e352a5bc34d03e966dd24603ed4853f5ff778c3170bb365861776e18c`

Проверены внутренние хеши, зависимости, версии UI/control, запуск встроенного control, capability, start/progress/cancel и авторизация в отдельном временном каталоге. Проверка не изменяет установленную системную службу. Установка этой версии, реальный VPN-трафик и запуск GUI остаются стендовой приёмкой. Публикация GitHub release оформляется после приёмки сборки.

Windows: выполнена кросс-компиляция Go; это не native execution. Android arm64: собрана новая libnaga.so; debug APK этим действием не обновлялся. Swift package tests выполнены на Linux; запуск подписанного приложения/Packet Tunnel на iPhone не проверен. Текущий SwiftUI ServersView не содержит кнопки массового замера; Swift-клиент сохраняет legacy метод. Добавление интерфейса заданий SwiftUI — отдельная задача согласно P04.09.

## Сценарии для ваших стендов

Используйте одинаковую подписку и контрольный URL. Начните с 1, 10, 50 и 100 узлов: все доступны, один медленный, 10% недоступны, половина недоступна, все недоступны. Запишите режим VPN, тип сети, холодное/повторное подключение. В отчёт не включайте URL подписки, токен control, серверные адреса и ключи.

| Стенд | Что проверить |
|---|---|
| Linux | Проверка с выключенным и включённым VPN; первые ответы до окончания списка; Cancel; Probe–Start/Stop; смешанный AWG/olcRTC; повторный запуск AppImage, tray и системная установка |
| Windows | Те же сценарии; остановка временных exe; сохранность активного туннеля/DNS; несколько повторных отмен; приватность файлов конфигурации |
| Android | Проверка при работающем VPN; одиночный Clash API путь; Cancel; background/resume; TUN lifecycle; отсутствие попыток запуска неподдерживаемого idle sing-box |
| iPhone | Совместимость legacy API и подписанного Packet Tunnel; Start/Stop, отмена при остановке control, отсутствие утечек туннеля; интерфейс async job после отдельной SwiftUI-задачи |

Для выбора лимита сравните 8/16/20 на ПК и 8/10 на Android при одинаковых узлах. Измерьте время первого/последнего результата, долю таймаутов, CPU, память, FD и влияние на обычный трафик. AWG: отдельно 1/2/4 подготовки; olcRTC: отдельно 1/2 процесса после проверки изоляции портов. До включения новых defaults эти сравнения остаются открытыми.

Для Karing/Naga выполните по пять прогонов в одинаковых условиях и запишите медиану/p95. Локальный разбор исходников Karing не заменяет этот эксперимент. Пункты P06.02/P06.03/P06.05, P08.04/P08.05, P09.06/P09.07 и части P11.02/P11.03/P11.05/P11.06 остаются открытыми до соответствующих измерений и стендовой приёмки.
