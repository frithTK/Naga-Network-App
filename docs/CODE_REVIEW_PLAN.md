# Подробный план code review Naga Network

Версия 2, 2026-10-13. План уточнён после проверки порядка действий, зависимостей, полноты охвата и критериев завершения.

Цель: получить доказательную оценку корректности, безопасности, устойчивости, совместимости платформ и сопровождаемости всего проекта. Результат — реестр охвата, воспроизводимые находки и очередь исправлений. Чекбоксы ниже относятся к будущему ревью проекта; проверка самого плана описана в разделе 9.

## 1. Что исправлено после проверки первой версии

| Недочёт | Исправление |
|---|---|
| Широкие этапы содержали несколько самостоятельных задач без отслеживания результата | Каждый шаг получил ID, действие и проверяемый результат |
| Привилегированные helper-процессы и автообновление шли после основного runtime и UI | Их проверка перенесена в S05, до глубокого ревью runtime |
| Изоляция упоминалась, но архитектура процессов и побочные эффекты тестов определялись после baseline | S01 определяет границы и стенды; запуск проверок начинается в S02 |
| Commit и diff не фиксируют содержимое новых файлов | S00 включает список и хеши исходных файлов рабочего дерева, в том числе untracked |
| Проверка loopback могла восприниматься как одинаковое требование ко всем точкам входа | Отдельно проверяются строгий StartLocal и CLI, допускающий адрес вне loopback при наличии токена; допустимость режима сверяется с требованиями |
| Повторялись проверки runtime, движков и платформ без владельца результата | Компонентные доказательства принадлежат S03–S08; выполнение на ОС — S09; сквозные сценарии ссылаются на них в S11 |
| Обычные тесты и полноценный fuzzing не были чётко разделены | Seed-примеры учитываются в S02; отдельные ограниченные fuzz-запуски — в S11 |
| Экспорт Swift-фикстур мог переписать проверяемые эталоны | Сначала сохранить исходные фикстуры, затем экспортировать в копии дерева и сравнить |
| Полное декартово произведение платформ/движков/режимов было не ограничено | Создаётся матрица применимости; неподдерживаемые сочетания проверяются на корректный отказ |
| Критерии завершения ревью требовали успешных тестов и частично смешивались с исправлением дефектов | Ревью завершается после проверки охвата и фиксации результатов, включая FAIL; готовность релиза и проверка исправлений оцениваются отдельно |
| Отсутствовали явная проверка применимых уязвимостей зависимостей и пределы доказательств | Добавлены provenance, достижимость уязвимого кода, версии сканеров и уровни доказательств |
| Повторяемость сборки могла трактоваться как побайтовая идентичность подписанных артефактов | Проверяются фиксированные входы и эквивалентность состава; подпись, timestamps и побайтовая воспроизводимость оцениваются отдельно |

Это исправления плана. Они не являются выводами о наличии дефектов в проекте.

## 2. Исходные факты и границы

- Основной код: Go в `core/` и `cmd/`, Flutter/Dart в `app/`, SwiftUI/SwiftPM в `ios/`. Объём при ознакомлении — около 52 тысяч строк исходников и тестов без сборочных каталогов.
- Движки: sing-box, userspace AmneziaWG и отдельный olcRTC. Для sing-box и AmneziaWG есть объединение узлов; выбранный olcRTC использует отдельный runtime.
- CI `.github/workflows/checks.yml` запускает Go tests/vet/выборочный race и Dart analyze/Flutter tests на Linux. Windows workflow собирает portable/setup, но не содержит отдельного шага запуска Windows-тестов.
- Текущая база при составлении — `2fe0f50043bdafe8cc59ee0e9a673f1a4ede31de` плюс незакоммиченные изменения и новые файлы. При начале ревью снимок обновляется.
- Основной iOS-путь — `ios/` через xtool. `app/ios/` — резервный Flutter/Xcode-каркас. В текущей SwiftUI-оболочке Go control-plane не запускается, а PacketTunnel возвращает ошибку до подключения ядра.
- Проверяются все исходные модули, тесты, конфигурации, сборщики, упаковка, документация и поставляемые ресурсы. Для сгенерированных файлов проверяются генератор, входы и результат. Локальные сборочные каталоги и сторонние исходники классифицируются отдельно.
- Автоматическое исправление всех находок, публикация релизов и доработка будущего iOS datapath — отдельные работы. Этот план задаёт проверку текущей реализации и предложения исправлений.

## 3. Как фиксировать результаты

Рабочие материалы будущего ревью размещать в `docs/testing/audit/<run-id>/` либо в отдельном каталоге отчёта. Этот путь уже исключён из git. Сам план остаётся в `docs/CODE_REVIEW_PLAN.md`.

Планируемые материалы:

| Материал | Содержимое |
|---|---|
| `baseline.json` | Commit, состояние дерева, перечень и хеши исходников, версии инструментов и бинарников |
| `coverage.csv` | Файл/модуль, платформа, владелец этапа, способы и результаты проверки, ссылки на доказательства |
| `architecture.md` | Процессы, IPC, потоки данных, привилегии, владельцы ресурсов и состояния |
| `requirements.md` | Ожидаемое поведение, источник требования и неустановленные гарантии |
| `matrix.csv` | Применимые сочетания платформы, движка, режима и сценария |
| `checks/` | Команды, exit codes, результаты тестов, причины SKIP и версии стендов |
| `findings.md` | Подтверждённые дефекты, гипотезы с недостатком доказательств и архитектурные предложения |
| `report.md` | Итог по охвату, находкам и готовности каждой платформы |

Для каждого шага: ID, проверенный снимок, входные условия, действие, ожидаемый и фактический результат, доказательство, ограничение. Статусы: `TODO`, `PASS`, `FAIL`, `UNAVAILABLE`, `N/A`. Для `UNAVAILABLE` и `N/A` нужны причина и следующий возможный способ проверки.

Чтение кода, static analysis, unit tests, сборка, выполнение на ОС/устройстве и сквозная проверка учитываются раздельно. Успешная компиляция не закрывает выполнение native-сценария. Процент покрытия не заменяет проверки важных ветвей.

| Этап | Зависит от | Основной результат |

| S02. Baseline и инструменты | S01 | Результаты доступных проверок и карта пропусков |

| S04. Импорт, преобразования, хранение | S03 | Проверка недоверенных данных и сохранности профилей |
| S05. Привилегии, IPC, автообновление | S01–S04 | Проверка наиболее опасных границ исполнения |
| S06. Runtime, policy, сеть | S03–S05 | Модель переходов и отката сетевых изменений |
| S07. Движки и native bridges | S04, S06 | Совместимость и владение ресурсами адаптеров |
| S08. Сборка, поставка, зависимости | S02, S05, S07 | Проверенные входы и артефакты для стендов |
| S09. Выполнение на платформах | S06–S08 | Результаты native-сценариев на каждой ОС |

| S11. Сквозные отказы, fuzz, нагрузка | S02/S04 для fuzz; S06/S07 для компонентной нагрузки; S09/S10 для сквозных сценариев | Подтверждение поведения на границах подсистем |
| S12. Отчёт и сверка охвата | Результаты S00–S11 | Находки, ограничения, приоритеты и итог |

Это рекомендуемый порядок одного ревью. Недоступность одного стенда ограничивает только зависимые сценарии: чтение кода и независимые проверки продолжаются. Гипотезы высокого риска проверяются сразу, как доступны необходимые условия.

S05 проверяет код и компонентные сценарии helper/updater; реальные установки и привилегированные операции выполняются в S09/S11 после S08. Полная проверка скриптов предшествует их запуску для платформенных сборок. До S02 отдельно читаются точки запуска самих baseline-тестов.

S11 выполняется частями: fuzzing парсеров можно начать после S04, компонентную нагрузку — после проверки соответствующего runtime/адаптера, а сквозные device-сценарии — после S09/S10. Недоступный iPhone не задерживает fuzzing или нагрузочные проверки Go.

## 5. Подробные шаги

### S00. Зафиксировать снимок и полный охват

- [ ] **00.01. База.** Записать полный commit, branch и состояние index/worktree. Результат: однозначное описание базы без переключения ветки или сброса изменений.
- [ ] **00.02. Незакоммиченный код.** Зафиксировать diff tracked-файлов и содержимое новых исходников в защищённой копии; получить их хеши. Результат: untracked iOS-код включён в снимок.
- [ ] **00.03. Исключения.** Разделить исходники, generated, vendor, build output, локальные настройки и реальные секреты. Результат: каждый исключённый путь имеет причину; секреты не копируются в общий отчёт.
- [ ] **00.04. Реестр.** Включить все исходные файлы, тесты, manifests, scripts, CI, packaging, документы и ресурсы в `coverage.csv`. Результат: файл не теряется между этапами.
- [ ] **00.05. Происхождение изменений.** Для будущих находок предусмотреть «существует в базе», «в текущем diff», «происхождение не установлено». Результат: регрессии отделяются от давних дефектов.
- [ ] **00.06. Изменение базы.** Установить правило: новые правки после снимка получают отдельный diff и проверку затронутых зависимостей. Результат: доказательства связаны с конкретной версией.

**Выход:** база и реестр полны. Файлы текущей реализации не изменены процедурой фиксации.

### S01. Построить архитектуру, требования и стенды

- [ ] **01.01. Точки входа.** Прочитать `cmd/naga-control`, `cmd/naga-windows`, `cmd/naga-android`, `cmd/naga-ios` и запуск клиентов. Результат: карта процессов каждой платформы.
- [ ] **01.02. Данные и IPC.** Проследить импорт → storage → config transforms → adapter → telemetry → API → UI. Результат: названы форматы, порты, pipes, channels и границы процессов.
- [ ] **01.03. Ресурсы.** Для TUN/fd, процессов, goroutines, DNS, proxy, маршрутов, sidecars и temp configs определить владельца и cleanup. Результат: таблица acquire/release, включая аварийный путь.
- [ ] **01.04. Требования.** Сверить README, платформенные документы, тесты и пользовательские гарантии. Результат: требования к Connected, обрыву VPN, IPv6, split, refresh и сохранению данных со ссылкой на источник.
- [ ] **01.05. Неопределённости.** Записать противоречия документов и поведения; отдельно обозначить неустановленные гарантии, например kill switch. Результат: отсутствие требования не выдаётся за подтверждённый баг.
- [ ] **01.06. Применимость.** Составить матрицу платформа × движок × TUN/proxy × установленный/portable/debug/release. Результат: поддерживаемые, условно доступные и неподдерживаемые сочетания.
- [ ] **01.07. Побочные эффекты тестов.** Прочитать setup/teardown, subprocesses и сетевые обращения baseline-проверок. Результат: тесты классифицированы как изолированные, сетевые или системные.
- [ ] **01.08. Набор входов.** Подготовить синтетические sing-box, envelope, AWG, olcRTC, subscription headers и повреждённые варианты. Результат: повторяемые fixtures без настоящих учётных данных.
- [ ] **01.09. Стенды.** Определить временные data dirs, mock servers, свободные порты, VM/devices и исходное состояние сети. Результат: системные сценарии имеют проверку восстановления и способ аварийного выхода.
- [ ] **01.10. Модель угроз.** Описать недоверенную подписку, удалённый источник, браузер, процессы того же/другого пользователя и подмену зависимости. Результат: для каждого субъекта установлены исходные права и границы защиты.

**Выход:** запуск S02 разрешён для классифицированных проверок; реальная сеть рабочей машины не используется как неявный тестовый стенд.

### S02. Выполнить baseline и оценить инструменты

- [ ] **02.01. Окружение.** Зафиксировать Go, Flutter/Dart, Swift, SDK/NDK, ОС и доступные sing-box/hev/olcRTC. Результат: версия и provenance каждого проверяемого бинарника.
- [ ] **02.02. Зависимости.** Проверить доступность модулей и lockfiles. При подготовке окружения сохранить исходные lockfiles и проверить diff после restore. Результат: тестируется зафиксированный набор зависимостей.
- [ ] **02.03. Go.** Запустить tests с JSON-результатами и coverage, затем vet. Результат: PASS/FAIL/SKIP каждого пакета и списка тестов, включая проверки реального sing-box.
- [ ] **02.04. Конкурентность.** Выполнить race для доступного на host кода, расширив текущий выборочный CI на остальные применимые пакеты. Результат: diagnostics, profile, androidvpn, winhelper и cmd не пропущены молча.
- [ ] **02.05. Flutter.** Выполнить Dart analyze и Flutter tests с coverage. Результат: ошибки анализатора, функциональные результаты и golden differences сохранены без обновления эталонов.
- [ ] **02.06. Swift.** Выполнить `swift test --package-path ios`. Результат: проверен Linux-совместимый API-модуль; SwiftUI/NetworkExtension не считаются проверенными этим запуском.
- [ ] **02.07. Исключённые ветви.** Сопоставить build tags, runtime skips и analyzer exclusions со списком платформ. Результат: отдельный список кода, который baseline не компилирует или не исполняет.
- [ ] **02.08. Качество тестов.** Проверить mocks, assertions, sleeps, условные skips, независимость тестов и cleanup. Результат: карта ложных гарантий и флейков с воспроизведением по необходимости.
- [ ] **02.09. Дополнительные анализаторы.** Оценить применимость ShellCheck, native linters и сканеров зависимостей. Результат: команды и версии согласованы со стеком; предупреждения требуют проверки контекста.
- [ ] **02.10. Первичный скан зависимостей.** Получить список применимых advisories с датой и источником на зафиксированных версиях. Результат: потенциальные риски видны до глубокого прохода; достижимость и влияние уточняются в S08.

Примеры baseline-команд из корня; путь coverage должен указывать на каталог конкретного отчёта:

```bash
go test -json -count=1 -coverprofile=/tmp/naga-review-go.cover ./...
go vet ./...
go test -race ./core/... ./cmd/...
swift test --package-path ios
```

Из `app/`:

```bash
dart analyze
flutter test --reporter expanded --coverage
```

Сохранить stdout/stderr и exit code каждого процесса. Coverage-путь Go в примере заменить на уникальный путь запуска; Flutter LCOV скопировать в каталог отчёта. Подготовку зависимостей выполнить до этих команд, если она необходима. Windows/mobile проверки вынесены в S09. Обычный `go test` исполняет seed corpus fuzz-тестов; поиск новых входов проводится отдельно в S11.

**Выход:** каждый запуск имеет зафиксированный результат. FAIL baseline открывает находку или задачу исследования, а не останавливает весь обзор кода.

### S03. Проверить API, контракты и диагностику

Охват: `core/control/server.go`, `serve_local.go`, auth/token в `cmd/naga-control`, Dart `control_plane_client`/`control_plane_token*`, Swift `NagaControlClient`, `core/diagnostics`.

- [ ] **03.01. Маршруты.** Перечислить все endpoint/method, вход, ответ, доступ, мутацию и владельца таймаута. Результат: полная маршрутная матрица.
- [ ] **03.02. Режимы доступа.** Проверить CLI production/dev/remote и строгий StartLocal. Результат: реальные разрешения и ограничения сравниваются с launch scripts каждой платформы.
- [ ] **03.03. Токен.** Проследить создание, чтение, права/ACL, обновление и потерю токена. Результат: доступы других пользователей и неавторизованных процессов проверены в заданной модели угроз.
- [ ] **03.04. HTTP-границы.** Проверить Host/Origin/CORS, redirects, DNS rebinding/CSRF в применимых условиях и передачу Bearer клиентами. Результат: запрос не получает неожиданные права.
- [ ] **03.05. Входные запросы.** Проверить методы, ID/path encoding, пустой/битый/слишком большой JSON, числа и неизвестные поля. Результат: ожидаемые ошибки без побочной мутации.
- [ ] **03.06. Согласованность.** Сверить Go/Dart/Swift DTO, enum, null/default, timestamp и единицы счётчиков. Результат: различия версий и обязательных полей покрыты контрактными сценариями.
- [ ] **03.07. Отмена и ошибки.** Проверить deadline клиента/сервера, отмену, повтор запроса и мутации во время polling. Результат: клиентская ошибка не скрывает завершившуюся мутацию или работающий runtime.
- [ ] **03.08. Фикстуры.** Сохранить исходные Swift fixtures; запустить exporter в отдельной копии и сравнить семантику ответов. Результат: обнаруженные расхождения не исчезают от перегенерации эталонов.
- [ ] **03.09. Приватность.** Проверить ответы, share/QR, сообщения исключений и logger на синтетических секретах. Результат: раскрытие соответствует назначению конкретного маршрута.
- [ ] **03.10. Журнал.** Проверить rotation, права, concurrent write/read/close, пределы клиентских событий и ошибки диска. Результат: журналирование не повреждает данные и не создаёт неограниченный ресурс.

**Выход:** маршруты и контракты имеют доказательства либо явные задачи проверки runtime-эффектов в S06/S11.

### S04. Проверить импорт, преобразования и storage

Охват: `core/subscription`, `core/profile` и вложенные парсеры, `core/storage`, `core/ruleset`, Dart fetch/link/file picker, Swift import.

- [ ] **12.07. Повторная проверка правок.** Если исправления входят в текущую работу, проверить соответствующий сценарий и затронутые границы на новой версии. Результат: прежнее доказательство не переносится на исправленный код автоматически.
- [ ] **12.08. Завершение.** Опубликовать локальный отчёт и итоговый реестр с FAIL/UNAVAILABLE. Результат: факт завершённого обзора не скрывает открытые дефекты или ограничения релиза.

**Выход:** отчёт позволяет оценить сделанную проверку и остаточный риск без чтения истории работы.

## 6. Минимальная сквозная матрица

| Сценарий | Вход/отказ | Что наблюдать |
|---|---|---|
| Импорт и повторный запуск | URL/file, clean data dir, restart | Оригинал, metadata, selection и поведение UI |
| Неверный импорт | Bad URL, oversize, malformed config, expired subscription | Ошибка, отсутствие повреждения прошлой версии |
| Переключение | Select/mode/policy, успешный и неудачный reconnect | Persisted mode, выбранный datapath, DNS/proxy/routes |
| Refresh активного профиля | Новый ключ/config, failed download/validation/start | Сохранность профиля и определённое состояние соединения |
| Конкурентность | Start/Stop/Select/Probe/Refresh с управляемыми задержками | State machine, отсутствие deadlock и stale UI |
| Аварийное завершение | Kill движка/control/UI/bridge в тестовом стенде | Владение процессами/fd, cleanup и recovery |
| Смена сети | Offline, class change, captive portal, background | Таймауты, reconnect и достоверность статуса |
| Отказ ОС | Consent/revoke/UAC/install cancel | Финальное состояние и возможность повторить |
| Обновление | Digest mismatch, missing asset, partial install, disk full | Целостность, version skew, rollback/restart |
| Длительная работа | Repeated sessions, many nodes, log/cache growth | CPU/RAM/fd/goroutines, latency и границы хранения |

Матрица не требует каждой комбинации всех измерений. Для каждой поддерживаемой ветви нужен базовый успешный путь и существенные отличающиеся отказы. Общие компонентные сценарии переиспользуются; неподдерживаемые комбинации проверяются на корректный отказ и объяснение в UI.

## 8. Находки и критерии завершения

Шаблон находки:

```text
ID / заголовок:
Проверенная версия / платформа / режим:
Приоритет / уровень подтверждения:
Условия и пользовательский эффект:
Путь, строка и символ:
Шаги / вход:
Ожидание и источник требования:
Фактический результат / доказательство:
Причина:
Предлагаемое исправление:
Регрессионная проверка:
Ограничения:
```

P0 — подтверждённая проблема с критическим эффектом и реалистичными условиями эксплуатации. P1 — значимый дефект безопасности, сохранности данных или основного сценария. P2 — ограниченный функциональный дефект/деградация с менее тяжёлым эффектом. P3 — локальный UI/documentation/maintainability дефект. Конкретная severity определяется эффектом и предпосылками, а не именем инструмента или категории.

**Ревью выполнено:** все файлы распределены, запланированные доступные проверки выполнены, FAIL/UNAVAILABLE объяснены, находки имеют доказательства и итоговый отчёт готов. Если остаются недоступные существенные сценарии, результат называется «ревью выполнено с ограничениями», а полная платформенная проверка остаётся открытой.

**Проверки исправления выполнены:** проверены новый diff, регрессия исходной ошибки и затронутые зависимости. Этот статус применим только при фактическом изменении кода.

**Готовность релиза:** отдельный вывод на конкретную сборку; учитывает открытые дефекты, отсутствующие обязательные проверки и фактически реализованные функции. Незавершённый iOS datapath не получает статус готового VPN по результатам тестов оболочки.

## 9. Проверка логики самого плана

При обновлении плана проверить:

- Все ID шагов уникальны, последовательны внутри этапа и имеют конкретное действие/результат.
- Зависимости ссылаются на существующие этапы и не образуют цикл.
- Архитектура/изоляция определяются до исполнения потенциально системных тестов.
- Компонентные, compile-only и device-доказательства разделены.
- Перегенерация fixtures/goldens не стирает исходное расхождение.
- Платформенные SKIP и build-tag exclusions отражены в реестре.
- Coverage и seed tests не выдаются за полную проверку поведения или fuzzing.
- Privileged execution/update проверяются до глубокого функционального прохода.
- Для общих проверок указан владелец, для недоступных комбинаций — причина.
- Условия завершения ревью допускают зафиксированный FAIL и сохраняют ограничения.
- Исправления, выпуск и будущая реализация не включаются в текущий scope неявно.
- Карта охвата соответствует фактическим каталогам репозитория.

При подготовке версии 2 сверены CI, точки входа CLI/StartLocal, Swift package и exporter, существующие fuzz targets, analyzer exclusions и платформенные build paths. Проверены структура документа, ID, зависимости и существование явно указанных путей. Это проверка плана; тесты приложения на этом этапе не запускались.
