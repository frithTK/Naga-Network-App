# AmneziaWG — подробные шаги доработки

Основание — [аудит AWG и сравнение клиентов](AWG_AUDIT_AND_PLAN.md). План начинается с падения control и покрывает запуск, внешний UDP-маршрут, проверку интернета, интерфейс и приёмку установленной сборки.

**Порядок работ.** Исправление двойного закрытия A1.01–A1.02 можно выпускать отдельно после регрессий A1.06. Полный стенд A0, подготовку A2 и тесты A3 можно делать параллельно. Платформенный маршрут из A2 — обязательное условие для приёмки системного туннеля на этой ОС. В A3–A4 сначала подтвердить выбранный вручную AWG на Linux, затем Auto и ручной режим с запасным вариантом. A5.03 можно выполнить раньше остальной диагностики. Прямой замер A6 зависит от контракта A3 и защиты сети A2. A7 определяет, пригоден ли туннель для пользовательского трафика, A8 подтверждает результат на установленной сборке.

Отмечать шаг выполненным по тесту или журналу. Для платформы указывать уровень проверки — сборка, компонент, устройство или реальный трафик. Отсутствие устройства оставляет соответствующую платформенную проверку открытой.

UDP relay поддерживает независимые потоки и несколько ответов. | Измерить нагрузку при 1/2/4 слотах, проверить DNS после переключения на установленном клиенте, QUIC, IPv6 и MTU под системным TUN. |

Зафиксировать область действия исключения и влияние на другие приложения с тем же IP назначения. При конфликте с чужой таблицей или невозможности защитить маршрут возвращать понятный отказ до активации AWG. При сверке маршрутов учитывать текущую политику split tunnel.

При смене uplink, шлюза или адреса peer подготовить новый путь и переключить его, затем освободить старый. Если прежний путь уже недоступен, приостановить отправку до новой защиты. Сигнал должен отражать фактическую сеть, поскольку текущий [обработчик](../core/control/runtime_probe.go#L783) пропускает события с прежним классом сети.

При освобождении последнего владельца удалять только собственное правило, которое всё ещё совпадает с установленным состоянием. Проверить замену правила извне во время сессии.

Поддержку IPv6 пользовательского трафика оценивать отдельно от защиты внешнего IPv6-сокета.

## A3. Разделить handshake, готовность TUN и доступность интернета

Начальные файлы — [sidecar.go](../core/engine/amneziawg/sidecar.go), [netstack.go](../core/engine/amneziawg/netstack.go), [runtime_awg.go](../core/control/runtime_awg.go), [runtime_select.go](../core/control/runtime_select.go), [адаптер sing-box](../core/engine/singbox/adapter.go).

- [ ] **A3.01.** Разделить конфигурацию и endpoint, готовность SOCKS, handshake нужного peer, применение TUN или proxy, HTTPS через outbound и пользовательский запрос через систему. Зафиксировать допустимый порядок на каждой платформе. Задать один предельный срок операции, лимиты этапов, отдельное время очистки и бюджет повторов. Уложить это в тайм-аут клиента или явно согласовать отмену и продолжение после завершения HTTP-запроса.
- [ ] **A3.02.** Читать состояние нужного peer из UAPI и привязывать его к текущему экземпляру устройства. Выбирать peer по маршруту тестового назначения в `AllowedIPs`. Для split tunnel без подходящего адреса использовать явно допустимую цель либо состояние «проверка интернета неприменима».
- [ ] **A3.03.** Инициировать handshake без keepalive трафиком к адресу, разрешённому профилем. Учитывать один бюджет вместо отдельных необязательных ожиданий. В тестах подтвердить одинаковый смысл успешной готовности для профилей с keepalive и без него.
- [ ] **A3.04.** Добавить HTTPS-проверку с проверкой сертификата, точным статусом 204 и отключёнными редиректами. Убедиться на стенде, что запрос к цели и его DNS идут через явно выбранный путь. Раздельно обозначать прямой тест через AWG SOCKS, тест outbound sing-box и системный тест. Одного значения `delay` Clash API для проверки статуса цели недостаточно.
- [ ] **A3.05.** Зарезервировать часть общего времени для независимой резервной HTTPS-цели. Различать отказ peer, ошибку HTTPS и неизвестную причину после тайм-аута. Повторять только ошибки, для которых резервная цель даст полезный результат. Записывать фактическую цель каждого замера. Отменённый запрос завершать без повторов.
- [ ] **A3.06.** Задать переходы для каждого режима. В строгом ручном режиме при подтверждённом handshake и установленном маршруте оставить выбранный туннель при отказе HTTPS, показать «доступ не подтверждён» и выполнять ограниченные повторы. В Auto и ручном режиме с запасным вариантом переходить к следующему кандидату только по правилам A4 и в пределах бюджета. Разделить «узлы недоступны» и «бюджет закончился, часть узлов не проверена». Для split tunnel состояние «проверка неприменима» не превращать в отказ узла. При отсутствии handshake, отказе защиты внешнего сокета или ошибке установки маршрута показывать отдельную причину и освобождать ресурсы.
- [ ] **A3.07.** Проверить 204, 503, редирект, отказ одной и обеих целей, DNS timeout, отсутствие handshake, профиль с несколькими peer и Stop на каждой стадии. При повторном запуске убедиться, что прежнее рукопожатие не подтверждает новую сессию. Для подтверждения системного пути выполнить отдельный пользовательский запрос после установки маршрутов.
- [ ] **A3.08.** Применить тот же контракт к периодическому health-check и восстановлению. Вручную выбранный узел не подменяется при отказе контрольной цели. В Auto и режиме с запасным вариантом исключить бесконечные переключения при общем сбое цели и проверить восстановление после временной потери связи. Контролировать свежесть текущих данных о peer с учётом отсутствия трафика в простое.

**Готово, когда** отказ контрольного сайта, молчание peer, неприменимая проверка и отмена различимы в результате. Успешный 204 через outbound подтверждает именно этот путь.
