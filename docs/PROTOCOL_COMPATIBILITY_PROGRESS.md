# Совместимость протоколов: ход работы

Дата начала: 2026-11-04. Исходный commit клиентской ветки `8915191`,
`origin/main` `d2e618a`. Задачи и границы готовности: [план](PROTOCOL_COMPATIBILITY_PLAN.md),
[подробные шаги](PROTOCOL_COMPATIBILITY_STEPS.md). Состояния ниже относятся к
локальному рабочему дереву и не означают опубликованный или установленный релиз.

## Выполнено локально

- Текстовый список olcRTC и массив `uris` разбирают несколько записей с
  сохранением порядка и имён. Для групповой сессии с разными ключами добавлен
  безопасный отказ с предложением выбрать отдельный узел: текущее YAML ядра
  использует один общий ключ.
- В конверте смешанные поддерживаемые и неподдерживаемые записи больше не
  скрывают поддерживаемые комнаты; preview, список профилей и UI сообщают о
  неполном наборе. При обновлении сохраняется прежний выбор, если он отсутствует
  в новой подписке; частичное обновление активной olcRTC-сессии отклоняется.
- Для старых выборов olcRTC добавлено сопоставление при обновлении: при
  перестановке комнат с одинаковыми именами сохраняется комната с тем же
  адресом; неоднозначное соответствие отклоняется. Это не заменяет постоянные
  серверные ID, которых текущая схема не содержит.
- Изменён порядок refresh активной olcRTC-сессии: подготовка выполняется до
  остановки, новая версия сохраняется после запуска; при отказе запуска или
  сохранения выполняется попытка восстановления старой. Если очистка TUN не
  подтверждена, повторный запуск не выполняется и возвращается ошибка. Логика
  отказов проверена компонентными тестами, системный rollback на устройстве
  ещё не подтверждён.
- Учёт обходных маршрутов olcRTC теперь сохраняет только успешно созданные
  маршруты. При конфликте или ошибке до включения туннеля откатываются только
  они, без перезаписи маршрута по умолчанию. Linux добавляет маршрут без
  `replace` и удаляет его с проверкой адреса, шлюза, интерфейса и протокола;
  конфликт и замена чужим маршрутом проверены в изолированном network namespace.
  IPv6-only адрес комнаты в текущем Linux IPv4-туннеле явно отклоняется. Для
  Windows изменение скомпилировано, но на Windows-устройстве не проверялось.
- Неизвестная или испорченная URI не возвращается из `RedactURI` целиком.
  Добавлены проверки нескольких комнат, разных ключей и неполного конверта.
- Строки комнаты и имени olcRTC корректно экранируются в YAML, включая обратные
  косые черты и управляющие символы; добавлена проверка сохранения значения.
- Неизвестные параметры транспорта в olcRTC URI больше не отбрасываются молча:
  такой узел считается недоступным и учитывается в предупреждении, а прямой
  запуск отклоняется. В двух URI текущего тестового профиля дополнительные
  параметры транспорта не обнаружены.
- Реализована передача параметров времени AWG 3 и диапазона
  `PersistentKeepalive` в текущий UAPI. Проверка создаёт устройство netstack и
  сопоставляет значения, прочитанные из реального UAPI, без внешней сети.
- AWG-конфиг с непустыми `J1–J3` или ненулевым `ITime` остаётся доступен для
  импорта, но запуск sidecar явно отклоняется: текущая UAPI их не принимает.
  Preview и обновление профиля предупреждают пользователя, при этом остальные
  узлы конверта остаются доступны. Неизвестные секции и поля, повторяющиеся
  присваивания и некорректные переключатели также больше не игнорируются при
  запуске; значения из конфигурации не попадают в сообщение об ошибке.
- После изменений прошли `go test ./...`, целевой `go vet`, `dart analyze` для
  изменённых файлов и полный набор из 139 Flutter tests; целевые Go tests также
  прошли с `-race`. Для Windows выполнена кросс-компиляция целевых пакетов;
  запуск Windows-тестов на устройстве не проводился. Команду `flutter analyze`
  прервал сбой анализатора LSP; отдельный `dart analyze` ошибок не нашёл.

## Изолированные проверки настоящих тестовых узлов

- AWG из тестового профиля: новый userspace sidecar установил рукопожатие и
  получил HTTPS 204 через SOCKS; системный TUN и маршруты не менялись.
- Кандидат olcRTC `b8a6e12`: на Linux собран отдельный временный бинарник,
  тесты upstream для MTS Link/VK Calls и config прошли. Временный SOCKS-процесс
  подключился к МТС Линк из тестового профиля и получил HTTPS 204. Процесс
  остановлен, временный конфиг удалён. Это не проверка системного TUN, DNS/UDP,
  смены сети, Android/Windows/macOS или установки опубликованного пакета.
- Проверка подписки через отдельный Linux sing-box `1.13.20` и его локальный
  API без системного TUN: повторный прогон успешно проверил HTTPS-трафик через
  все доступные на тот момент 6 VLESS, 4 TUIC и 4 Hysteria2 outbound. В первом
  прогоне для каждого протокола был один отказ; в следующих прогонах отдельные
  запросы восстанавливались после повтора. Причина временных ошибок не выяснена;
  проверка не покрывает системный DNS, UDP-трафик пользователя и другие ОС.
- Для Linux подготовлен [изолированный эксперимент SO_MARK](../scripts/olcrtc/README.md)
  с защитой сокетов upstream olcRTC `b8a6e12`: отдельное сетевое пространство
  проверяет маршрутизацию защищённого TCP, Pion UDP и DNS-транспорта, а также
  запрет запуска сокета при отсутствии прав на метку. Это компонентный тест
  механизма, без настоящего TUN и без включения в поставку приложения.
- Повторная проверка 2026-11-20 для upstream `b8a6e12`: прошли тесты
  `internal/auth/mtslink`, `internal/engine/mtslink`, `internal/config`,
  `internal/gate` и изолированный эксперимент SO_MARK. Upstream gate
  допускает для MTS Link транспорт `vp8channel`; адрес медиа-сервера
  получается динамически. Это по-прежнему не проверка системного VPN.
- Повторная изолированная проверка тестовой комнаты 2026-11-20 после сборки
  отдельного кандидата не подтвердила соединение: процесс завершился до открытия
  SOCKS с сетевым timeout. Обычный HTTPS-запрос без VPN в это время получил 204;
  отдельно DNS-сервер движка ответил на UDP-запрос.
  Причина timeout не установлена; прежний успешный результат не доказывает
  доступность этого узла сейчас. Системные маршруты при проверке не менялись.
- При следующей диагностике актуальная подписка содержала ту же комнату, ключ
  и транспорт MTS, что сохранённый профиль. На компьютере также обнаружены
  активные правила другого VPN, направляющие внешний трафик через отдельный
  туннель; их влияние на timeout не установлено. Для будущей интеграции добавлен
  консервативный детектор нестандартных policy rules, проверенный в отдельном
  network namespace. Он пока не вызывается runtime и не резервирует ресурсы.
- Повторная проверка 2026-11-20: актуальная подписка отдаёт четыре записи
  `amnezia.confs` (PL, LV, CA, CZ); `amnezia.conf` совпадает с PL. Клиент
  отображает каждую запись отдельно, сохраняет выбор страны при перестановке
  и отклоняет обновление, если выбранная страна исчезла. Проверены разбор,
  переключение, недоступный узел и перезапуск на синтетическом профиле; все
  четыре настоящих конфига независимо установили handshake и получили HTTPS
  204 через отдельные SOCKS-процессы без изменения системных маршрутов.
  Установленный control-plane вернул все четыре узла в API. Системный TUN и
  переключение этих стран в установленном приложении после обновления ещё не
  проверялись.

## Открыто

- Диагностика приложения дополнена проверкой системного HTTPS с повтором;
  успешный ответ не подтверждает прохождение через TUN. Проверки пути через
  VPN, внешнего адреса, системного DNS и UDP остаются отдельной задачей.
  Проверка узлов уже использует HTTPS через конкретный outbound; для olcRTC
  теперь требуется ответ 204 без перенаправления. Изменения пока локальные.

- 2026-11-20: последняя попытка установленного клиента завершалась на
  `prepare_profile` с `selected mode is not available in profile`. Когда
  запускается отдельный AWG-профиль, сохранённый выбор AWG в другом конверте
  применялся к его sing-box до добавления AWG. Это исправлено и проверено
  компонентным тестом; собран локальный AppImage и установлен его runtime.
  Системное подключение и трафик после исправления пока не проверены: на хосте
  действуют policy rules другого VPN. Старый AppImage при запуске может снова
  установить свой runtime; для проверки нужно использовать исправленный пакет.
- Последующая попытка пользователя снова запустила исходный установленный
  AppImage и вернула старый runtime. Исправленный пакет установлен на место
  запускаемого через ярлык, исходный сохранён в каталоге приложения как
  `NagaNetwork-1.2.9-original.AppImage.backup`; служба перезапущена. Реальный
  трафик через системный TUN после этого всё ещё не подтверждён.

- МТС Линк ещё не включён в клиентский runtime: необходимо согласовать версию
  движка и системную маршрутизацию, включая адреса сигнализации и WebRTC/SFU,
  затем проверить TUN и очистку на заявленных платформах. Нельзя считать успех
  отдельного SOCKS-процесса готовностью системного VPN.
- Постоянные серверные ID, проверка rollback активного refresh на устройстве,
  проверка нескольких AWG в системном TUN и проверка старых клиентов остаются
  открытыми. Значение `J1–J3`/`ITime` для других реализаций AWG и обработка
  прочих неизвестных полей ещё требуют сверки с конкретными форматами.
- Нужны повторная проверка после дальнейших изменений, пакетные сборки и
  реальные проверки устройств; тестовый профиль не раскрывать в отчётах.
