# План ускорения проверки серверов

Дата: 2026-10-14. Основание: [разбор Karing и Naga](KARING_LATENCY_REVIEW.md), Naga 1.2.6.
Отмеченные пункты реализованы и проверены локально. Подробности и границы проверки — в [отчёте выполнения](LATENCY_IMPLEMENTATION.md); стендовые пункты остаются открытыми.

## Цель и измеримые критерии

Первый готовый результат появляется во время проверки остальных узлов. Недоступный узел не задерживает отображение уже полученных ответов. Полная проверка использует ограниченное число запросов и процессов и освобождает свои ресурсы после отмены.

Измерять отдельно:

- время от нажатия кнопки до первого результата;
- задержку между готовностью результата в control и его отображением;
- длительность подготовки движков, каждой группы протоколов и всей проверки;
- завершённые, недоступные, отменённые и пропущенные узлы;
- максимальное число одновременных запросов/процессов, CPU, память и файловые дескрипторы.

Цель для выдачи готового результата — до 500 мс в контролируемом тесте при открытом экране. Время ответа самого сервера сюда не входит. Полная длительность реального списка и выбранный параллелизм определяются измерениями; наличие недоступных узлов учитывается отдельно.

## Основные решения

1. Новая массовая проверка работает как фоновое задание control. Flutter получает изменения через опрос прогресса примерно раз в 300 мс; одновременно выполняется один запрос прогресса.
2. Начало, чтение прогресса и отмена имеют отдельные API. Старый `POST /v1/nodes/probe` сохраняет прежний формат ответа и использует тот же механизм проверки, ожидая его окончания.
3. Одновременно допускается одно ручное задание на control. Подготовка, sing-box, AWG и olcRTC входят в него. Автовыбор и периодические проверки здоровья имеют собственное назначение и приоритет.
4. Проверка владеет своим context, временными процессами, портами и файлами. Изменение состояния VPN или профилей проверяется через поколение runtime и ревизии входных данных.
5. Результат передаётся сразу после завершения узла. Успешный HTTP-тест, таймаут, отмена и отсутствие возможности выполнить проверку различаются.
6. Сначала исправляется ожидание интерфейса. Параллелизм, подготовка движков и отдельные транспорты меняются последующими проверяемыми коммитами.

## P01. Ввести жизненный цикл задания

Файлы: [runtime.go](../core/control/runtime.go), [runtime_probe.go](../core/control/runtime_probe.go); новый модуль управления заданиями проверки.

- [x] **P01.01.** Описать задание: `job_id`, поколение runtime, ревизия профилей, время начала, общий deadline, состояние, счётчики, ревизия прогресса и cancel function. Обнаружение полного списка узлов выполняется в фоне; пока оно не окончено, total может быть неизвестен.
- [x] **P01.02.** Зафиксировать состояния задания: preparing/running/cancelling/completed/cancelled/timed_out/failed. Завершение подтверждается `cleanup_complete=true` после освобождения принадлежащих заданию ресурсов. При превышении grace публикуется failed с `cleanup_complete=false`; задание сохраняет владение до закрытия ресурсов и запрещает повторный запуск.
- [x] **P01.03.** Регистрация задания и чтение его снимка не выполняют сетевой I/O, запуск процессов или длительное чтение профилей. Использовать короткую отдельную синхронизацию прогресса; задокументировать порядок захвата mutex.
- [x] **P01.04.** Повторный запуск при активном задании возвращает его идентификатор и конфликт, не создаёт новый пул. После отмены новое задание стартует после завершения cleanup предыдущего, особенно при проверке с выключенным VPN.
- [x] **P01.05.** Отмена доступна до захвата длительных runtime/mutation locks. Start, Stop, замена движка, восстановление соединения и удаление/изменение участвующего профиля отменяют либо инвалидируют соответствующую проверку до замены её ресурсов.
- [x] **P01.06.** Каждый результат перед записью сверяется с job_id, поколением runtime и ревизией узла. Поздний callback старого задания не изменяет новую проверку или кеш новой сессии.
- [x] **P01.07.** Context фоновой задачи принадлежит control и ограничен deadline. Передать его через уже существующие подготовку config/rule sets, запуск и Ready AWG/olcRTC, sing-box и HTTP measurement до введения нового API; это базовая правка отмены, а не будущая оптимизация параллелизма. Завершение HTTP-запроса регистрации не отменяет задачу. Legacy-запрос, явная отмена, остановка control и runtime lifecycle передают отмену по явно описанным правилам.
- [x] **P01.08.** Финализация идемпотентна. Она закрывает только собственные процессы, sockets, файлы и sidecars; borrowed live runtime остаётся под владельцем VPN. Ожидание workers/процессов выполняется вне locks, нужных для прогресса и отмены.

**Приёмка:** проходят регистрации Start–Start, Probe–Probe, Probe–Stop, Probe–Start, отмена во время подготовки, отмена после готового результата и поздний callback. После завершения отсутствуют оставшиеся временные ресурсы. При зависающей подготовке progress/cancel endpoints остаются отзывчивыми.

## P03. Добавить API прогресса с совместимостью

Предлагаемый контракт:

| Запрос | Поведение |
|---|---|
| `POST /v1/nodes/probe/start` | Быстрая регистрация; `202` с job_id и начальным снимком |
| `GET /v1/nodes/probe/jobs/active` | Активное задание или null; восстановление после открытия приложения |
| `GET /v1/nodes/probe/jobs/{job_id}` | Состояние, ревизия, счётчики и результаты |
| `POST /v1/nodes/probe/jobs/{job_id}/cancel` | Идемпотентный запрос отмены; cancelling до окончания cleanup |
| `POST /v1/nodes/probe` | Прежний блокирующий ответ со списком узлов |

- [x] **P03.01.** Зафиксировать JSON-структуры, терминальные состояния и ответы: 401 для отсутствующей авторизации, 404 для неизвестного/истёкшего job_id, 409 с active job_id для повторного запуска, 400 для неверных параметров.
- [x] **P03.02.** Применить существующую token authorization к новым endpoints до любого изменения job. Неавторизованные Cancel/Stop не отменяют проверку. Регистрация и отмена не ждут длительный общий mutation lock; состояние проверяется собственным механизмом P01.
- [x] **P03.03.** Добавить capability `node_probe_jobs` в health. Новый клиент выбирает API по capability, старый клиент продолжает использовать существующий контракт.
- [x] **P03.04.** Поддержать `after_revision`: отдавать изменившиеся строки и счётчики. Первое чтение возвращает полный снимок. При удалении истории или рассинхронизации клиент получает признак обязательного полного снимка.
- [x] **P03.05.** Стартовая политика хранения: одно активное и одно последнее терминальное задание, TTL терминального — 5 минут. Для каждого узла хранить текущее состояние и его последнюю ревизию; delta возвращает актуальные изменившиеся строки, а не бесконечный журнал переходов. Список узлов и размер metadata ограничены; после сценариев 100/1000 узлов проверить память этой политики.
- [x] **P03.06.** Для legacy handler сохранить прежние коды ошибок и JSON списка. Он ожидает тот же job engine, без отдельной второй реализации проверок. Правило отмены legacy-потребителем учитывать явно.
- [x] **P03.07.** Проверить сценарии новый UI/старый control и старый UI/новый control. Ответ 401 или повреждённый JSON не служит поводом повторять запуск через legacy API.

**Приёмка:** start/progress/cancel отвечают независимо от медленного узла; registration не выполняет полный прогон. В контролируемом тесте start/progress отвечают до 500 мс. Контракт прежнего endpoint сохранён.

## P10. Согласовать метрику, бюджеты и диагностику

- [x] **P10.01.** Фиксировать фактический URL и HTTP/HTTPS-схему. Учесть, что текущий Clash delay endpoint сбрасывает переданный HTTP URL. Исправить неточные комментарии и пояснения метрики.
- [x] **P10.02.** До изменения таймаутов сравнить фактические результаты. Затем согласовать общий бюджет работы от регистрации: подготовка + очереди + HTTP. Cleanup имеет отдельный grace 5 секунд, выполняется вне locks и входит в измеренную полную длительность. Если Stop не вернулся, API сообщает failed/cleanup_complete=false и сохраняет задание; новая проверка и Start не запускают замещающие ресурсы. Stop работающего VPN остаётся доступен. Позднее завершение cleanup меняет ревизию и cleanup_complete. Ожидание клиента состоит из коротких запросов progress, а не одного 200-секундного POST.
- [x] **P10.03.** Индивидуальный timeout ограничен оставшимся бюджетом. При общем timeout остановить постановку новых работ, отменить начатые и сохранить готовые результаты.
- [ ] **P10.04.** Добавить безопасную диагностику этапов: queued/preparing/checking, elapsed, counts, timeout reason и выбранный предел. Оценить нагрузку самого polling и размер delta response.
- [x] **P10.05.** Проверить, что ручная проверка списка не выбирает другой активный узел, не объявляет Connected и не меняет счётчик health/failover. Измеренная задержка активного узла применяется с проверкой свежести.

**Приёмка:** понятно, какая стадия занимает время. Таймаут и пропуск различимы; короткие настройки не создают фиктивных успешных результатов или ложного отключения VPN.

## Проверка логики плана

| Проверенный вопрос | Решение |
|---|---|
| Можно ли сразу публиковать кеш без владельца? | P01 предшествует P02: job_id/поколение защищают от результатов старого задания |
| Можно ли вернуть 202 и продолжить на r.Context? | Задача владеет отдельным context; lifetime HTTP-регистрации описан отдельно |
| Может ли progress или cancel ждать запуск VPN? | Отдельная короткая синхронизация; никакого ожидания сетевых операций/cleanup под mutex прогресса |
| Сломаются ли прежние клиенты? | Старый endpoint/JSON сохранены, новый механизм определяется capability |
| Как восстановить проверку после потери локального job_id? | Endpoint active возвращает текущее задание; терминальные снимки имеют ограниченный TTL |
| Где находится передача отмены в тяжёлые helpers? | Она включена в P01 до нового API, а P08/P09 сохраняют её при оптимизации |
| Что считать общим deadline и временем завершения? | Deadline ограничивает работу; cleanup отдельно ограничен и учитывается в полной длительности |
| Достаточно ли увеличить число goroutines? | Пул уже есть; сначала исправляется выдача, затем измеряются пределы и общая нагрузка |
| Помогут ли меньшие таймауты сами по себе? | Таймаут Karing длиннее; до изменения бюджета исправляется очередь и отображение |
| Что делать, если Stop временного процесса не вернулся за grace? | Ошибка и cleanup_complete=false, владение остаётся у задания; повторный запуск запрещён до фактической очистки |
| Можно ли запускать несколько olcRTC на 10808? | Изоляция endpoint/config/readiness выполняется до параллелизма |
| Что делать при Start/Stop/обновлении профилей? | Явная отмена/инвалидация, revision checks, cleanup только owned ресурсов |
| Существует ли общий бюджет после sing-box? | Он переносится на всё задание, включая подготовку AWG и olcRTC |
| Как трактовать отменённый или ещё не проверенный узел? | Отдельные состояния, без нового failed-замера и фиктивного нулевого ping |
| Можно ли обещать первые ответы за 500 мс после клика в любой сети? | Критерий относится к выдаче уже готового результата; время соединения/подготовки измеряется отдельно |
| Есть ли сравнение с запущенным Karing? | Пока только разбор исходников и локальный proof Naga; одинаковый стендовый прогон входит в P11 |

Отметка [x] относится к реализации и указанным локальным регрессиям, а не ко всей платформенной приёмке этапа. Открыты сравнения нагрузки и скорости на реальных узлах, проверка VPN-пакетов/GUI на стендах и установка новой сборки. Пределы запросов: 8 по умолчанию, максимум 20 на ПК / 10 на мобильных платформах; AWG и olcRTC — по одному временному процессу. P11.02/P11.03/P11.06 частично выполнены; подробности — в отчёте.
