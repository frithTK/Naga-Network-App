# Аудит AmneziaWG и план доработок

21 ноября 2026 года. Проверены рабочие исходники Naga поверх `8915191`, включая параллельный запуск AWG, и установленные Linux-компоненты Naga 1.2.9 с sing-box 1.13.20. Движок AWG в исходниках и установленном control — amneziawg-go v3.1.20260828.

Сейчас задержки возникают в трёх местах: подготовка всех узлов до старта, проверка HTTPS перед подключением и последовательные ручные замеры AWG. Ошибки рукопожатия и проверки HTTPS выглядят почти одинаково. Отдельно подтверждены падение control на ошибке настройки AWG и положительный замер при HTTP 503 от контрольного сервера. Первые задачи — исправить падение, определить реальный маршрут AWG-пакетов и разделить состояния туннеля и HTTPS.

## Что произошло на Linux

| Попытка 21 ноября | Что записал Naga |
|---|---|
| 18:07 | Латвийский и канадский AWG по очереди потратили около 12 с на ожидание рукопожатия. После этого два запроса проверки польского AWG завершились локальным HTTP 504 примерно через 8 с каждый. Naga остановила подключение через 42 с. |
| 18:33 | Снова около 24 с ожидания двух других узлов. Польский AWG прошёл проверку, запуск занял 32,6 с. Сам этап проверки занял 5,8 с, а в результате замера было 395 мс. Эти числа измеряют разные интервалы. |
| 18:41–18:42 | В замерах нескольких протоколов были тайм-ауты системного DNS. Они записаны отдельно от двух попыток AWG. |

Все четыре endpoint в сохранённой подписке заданы IPv4-адресами. По этим событиям нельзя установить, шёл ли AWG UDP через физическую сеть после включения TUN, какой именно этап исчерпал бюджет HTTPS и использовал ли телефон тот же профиль. Позднее присутствие другого VPN не устанавливает причину прежних отказов.

## Найденные проблемы

| Приоритет | Факт | Последствие |
|---|---|---|
| P0 | При ошибке настройки UAPI или запуска устройства `Start` вызывает `dev.Close()`, затем повторно закрывает принадлежащий устройству netstack TUN. На Linux обычный профиль с доменным `Endpoint` проходит парсер, но `StdNetBind` ожидает числовой `AddrPort`. В локальной проверке ошибка UAPI привела к `panic: close of closed channel` в отдельном процессе. [Запуск sidecar](../core/engine/amneziawg/netstack.go#L60) · [Парсер](../core/profile/amneziawg/parse.go#L369) · [AWG bind](https://github.com/amnezia-vpn/amneziawg-go/blob/v3.1.20260828/conn/bind_std.go#L90) · [Закрытие устройства](https://github.com/amnezia-vpn/amneziawg-go/blob/v3.1.20260828/device/device.go#L422) | Ошибка одного профиля может завершить общий control. Доменные профили требуют отдельного исправления совместимости. |
| P1 | Нативный AWG UDP создаёт собственный `conn.NewDefaultBind()`. Интеграция Naga здесь не задаёт интерфейс, метку или защиту сокета. Настройка `auto_detect_interface` действует в sing-box, SOCKS указывает на loopback. [AWG bind в Naga](../core/engine/amneziawg/netstack.go#L64) · [SOCKS outbound](../core/profile/amneziawg/wrapper.go#L30) · [Настройка sing-box](../core/profile/profile.go#L713) | После включения TUN или смены сети наружный UDP зависит от маршрутов ОС. Потеря собственного маршрута — гипотеза для стендовой проверки. |
| P1 | `Ready` с keepalive ждёт рукопожатия, без keepalive выполняет пробное подключение к фиксированному адресу и возвращает готовность даже без рукопожатия. `IpcGet` сводится к первой записи peer. Отмена при ожидании превращается в ошибку рукопожатия. Оба варианта keepalive проверены на недоступном синтетическом peer. [Готовность](../core/engine/amneziawg/netstack.go#L100) · [Состояние peer](../core/engine/amneziawg/netstack.go#L145) | Один статус обозначает две разные вещи. Для нескольких peer состояние зависит от того, чья запись оказалась первой. |
| P1 | При старте проверка через Clash API использует один жёстко заданный URL. Положительное значение `delay` считается успехом. Проверка установленного sing-box на локальном TLS-сервере дала Clash API 200 и ненулевой `delay` для ответов целевого сервера 204 **и 503**. Сам Clash API возвращает 504, когда истекает его бюджет. [Клиент Clash API](../core/engine/singbox/adapter.go#L589) · [Измерение sing-box](https://github.com/SagerNet/sing-box/blob/v1.13.20/common/urltest/urltest.go#L115) · [Причина локального 504](https://github.com/SagerNet/sing-box/blob/v1.13.20/experimental/clashapi/proxies.go#L225) | Успешный замер подтверждает получение HTTP-ответа через outbound. Текущий код использует его как проверку доступности VPN. Тайм-аут при исправном туннеле может сорвать запуск, а ошибочный HTTP-ответ может пройти проверку. |
| P1 | Параллельная подготовка AWG ждёт все группы по четыре и только потом передаёт результаты вызывающему коду. Это происходит даже при явно выбранном другом узле. Автовыбор после запуска также ждёт все результаты группы. [Подготовка](../core/control/runtime_awg.go#L233) · [Старт смешанной подписки](../core/control/runtime_awg.go#L125) · [Проверка группы](../core/control/runtime_select.go#L60) | На подписке из четырёх узлов два соседских тайм-аута больше не складываются, но выбранный исправный узел всё ещё может ждать до 12 с. При большем списке добавляются следующие группы. |
| P1 | Главный экран при отсутствии текущего замера может взять значение рекомендованного узла в режиме Auto. Ручной API сводит большинство отказов к `probe_failed`. Tooltip успешного замера уже объясняет его смысл, однако короткое «нет ответа» скрывает причину. [Главный экран](../app/lib/main.dart#L4370) · [Причины замера](../core/control/probe_jobs.go#L395) · [Подсказка строки](../app/lib/main.dart#L4744) | На главном экране возможны миллисекунды другого узла. Пользователь не может отличить отказ handshake от ошибки DNS или контрольного сайта. |
| P2 | При отключённом VPN один worker обрабатывает AWG по очереди и поднимает временный sing-box для каждого профиля. Параллельный запуск VPN эту ветку не меняет. [Ручной замер AWG](../core/control/runtime_probe.go#L434) | Поздний рабочий узел ждёт подготовки и тайм-аутов предыдущих. Асинхронный API при этом уже умеет публиковать результаты по мере их готовности. |
| P2 | Для нескольких самостоятельных AWG профилей общая DNS-конфигурация берётся с первого успешно подготовленного профиля. Последующие узлы добавляются как SOCKS outbounds без изменения DNS detour. UDP relay в локальном SOCKS обрабатывает датаграмму, ждёт один ответ до 5 с и закрывает удалённое соединение, затем берёт следующую. [Сборка AWG-only](../core/control/runtime_awg.go#L53) · [DNS](../core/profile/amneziawg/wrapper.go#L93) · [UDP relay](../core/engine/amneziawg/socks.go#L156) | После переключения системное разрешение имён может зависеть от предыдущего узла. Потерянный UDP-ответ может задержать другие запросы в той же ассоциации. Нужны отдельные проверки DNS, UDP и QUIC. |

## Порядок реализации

[Подробные шаги, зависимости и критерии готовности](AWG_IMPLEMENTATION_STEPS.md). Исправление двойного закрытия можно проверить и выпустить отдельно. Для системного VPN обязательна проверка маршрутов и очистки на заявленной платформе.

1. **P0. Исправить владение TUN и обработку endpoint.** Закрывать TUN ровно один раз во всех ветках ошибки. Разбирать адрес и порт до создания устройства. Разрешать доменное имя через bootstrap DNS в пределах общего бюджета, передавать в UAPI числовой endpoint и сохранять исходный профиль. Принимать IPv4 и IPv6, различать ошибку адреса, DNS и отмену. Проверить, что неудачная конфигурация возвращает ошибку узла, control остаётся доступен, следующий Start проходит, FD и горутины освобождаются.

2. **P1. Вынести маршрутизацию наружного UDP в контракт AWG.** На Linux воспроизвести путь до peer в отдельном network namespace до и после включения системного TUN. Сравнить точечный маршрут и маркировку сокета с учётом полномочий control. На Android защитить IPv4/IPv6-сокеты через мост к `VpnService`, включая повторное открытие. Для Windows определить эквивалент с привязкой к исходящему интерфейсу или узким маршрутом. Проверить смену Wi-Fi, смену IP endpoint, совместную работу с DNS и удаление только собственных маршрутов на Stop/Cancel. Критерий — наружный UDP идёт по ожидаемому uplink, пользовательский трафик по политике выбранного VPN.

3. **P1. Разделить готовность SOCKS, handshake и доступность интернета.** Передавать отдельные стадии и причины от движка до UI. Подтверждать рукопожатие нужного peer в текущей сессии. HTTPS-проверка через выбранный путь ожидает 204, использует общий бюджет и при допустимом отказе проверяет независимую резервную цель. В строгом ручном режиме при валидном handshake и маршруте сохранить выбранный туннель и показать «доступ не подтверждён». Применять этот контракт при старте, периодической проверке и восстановлении.

4. **P1. Убрать необязательные узлы с пути подключения.** В строгом ручном режиме поднимать выбранный AWG, а для других явно выбранных протоколов не ждать подготовки AWG. В Auto и ручном режиме с запасным вариантом использовать ограниченную очередь с действующими приоритетами. Ограничить одновременный запуск профилей с конфликтующим портом или идентичностью peer. Сохранить доступ к незагруженным узлам для смены сети и автоматического восстановления через контролируемое переключение. В синтетическом стенде с одним быстрым и тремя зависшими узлами дополнительные узлы должны добавлять к запуску выбранного не более 500 мс.

5. **P1. Показывать верный замер.** Положительный результат называть «HTTPS-задержка» в деталях. Передавать `node_id`, источник замера, время и идентификатор цели. На главном экране подставлять только применимый результат активного узла во время сессии. До подключения рекомендация может показывать свой замер с явной подписью. Выделить «Рукопожатие не получено», «Истекло время HTTPS-проверки», «Проверка отменена», «Узел ещё не загружен». Проверить, что старое значение, замер другого профиля с тем же именем, смена сети или цели и отмена не порождают ошибочный пинг.

6. **P2. Ускорить ручные замеры и проверить пользовательский трафик.** Сравнить прямой HTTPS-замер через временный AWG SOCKS с live-проверкой через sing-box. У них разные пути, поэтому хранить источник результата. Сохранить очередь, общий deadline и отмену. Измерить лимиты подготовки 1/2/4, CPU, память и число сокетов. Для AWG-only согласовать системный DNS с активным узлом и проверить переключение, когда прежний DNS недоступен. Проверить параллельные UDP-запросы, несколько ответов одной ассоциации, QUIC, IPv6 и MTU. Если SOCKS остаётся узким местом, отдельно сравнить исправленный UDP relay с нативным datapath на приёмочном стенде.

## Приёмка на стенде

- Сначала сравнить установленные Naga 1.2.9 и кандидат на одном Linux-компьютере с одинаковым сохранённым профилем. Затем сравнить AmneziaVPN и Naga на одном AWG-конфиге и uplink. Karing и FlClash включать в отдельный прогон измерений, только если совпадают тип прокси и контрольная цель.
- Варьировать 1/4/12 узлов, ручной выбор и Auto, холодный и повторный запуск, IPv4/IPv6, TUN и системный прокси, недоступную цель и недоступный peer. На Android повторить запуск, переключение Wi-Fi/мобильной сети и Stop. Windows требует отдельной проверки маршрутов, macOS и iOS — отдельной проверки доступных native путей.
- Снять время до handshake выбранного peer, готовности TUN, первого валидного HTTPS через outbound и первого пользовательского запроса через системный VPN. Для ручного замера снять время первого и последнего результата, число тайм-аутов и ресурсы. В журнал писать этап, время и обезличенный код причины. Для p95 собрать хотя бы 30 прогонов на ключевой сценарий и публиковать размер выборки вместе с медианой и p95.
- Принимать пакет после проверки фактического трафика TCP, UDP и DNS через установленный кандидат, восстановления после смены сети и исправного Stop/Cancel. Отдельно зафиксировать сценарий, где HTTPS через outbound проходит, но системный маршрут ведёт в обход VPN.

## Проверки этого аудита

- Четыре целевых пакета Go прошли повторный прогон с `-race -count=1`: control, профиль AWG, движок AWG и sing-box.
- Изолированные проверки подтвердили двойное закрытие при ошибке настройки, различие `Ready` с keepalive и без него и принятие HTTP 503 как успешного `delay` установленным sing-box. Проверки использовали синтетические данные и локальные сокеты.
- Результаты прежней работы по асинхронным задачам и импорту находятся в [отчёте о замерах](LATENCY_IMPLEMENTATION.md) и [отчёте о совместимости](PROTOCOL_COMPATIBILITY_PROGRESS.md). Проверка с реальным трафиком на одинаковых профилях остаётся частью приёмки.
