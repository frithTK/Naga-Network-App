## Что они измеряют

В опубликованном ядре [URLTest](https://github.com/KaringX/sing-box/blob/73603b201141ee9bab41af76995808ccfc45209f/common/urltest/urltest.go#L70)
открывает TCP-поток через выбранный outbound и выполняет HTTP HEAD к контрольному URL. При HTTPS сюда входит TLS к контрольному серверу. Для QUIC-протокола поток идёт через его транспорт; это не ICMP-пинг адреса VPN-сервера.

Naga тоже использует Clash API `/proxies/{tag}/delay`, который вызывает URLTest в sing-box. Простая замена GET на HEAD в нашем control не ускорит эту ветку: HEAD уже выполняет ядро. GET относится к запросу локального API, а не к загрузке страницы через VPN.

## Подтверждённые различия

| Свойство | Karing, опубликованный клиент | Naga 1.2.6 |
|---|---|---|
| Ручная массовая проверка | Пул по умолчанию 20 на ПК, 10 на остальных платформах | Фиксированный пул 8 |
| Очередь | Освободившийся слот берёт следующий узел | Освободившийся worker тоже берёт следующий узел; эта часть уже реализована |
| Публикация результата | Значение узла обновляется после его проверки, отправляется событие | Все результаты сначала собираются; кеш обновляется после завершения всех workers |
| Отрисовка | Проверенные строки могут перерисовываться раз в секунду во время общей проверки | POST возвращает список в конце, Flutter ждёт весь ответ |
| Таймаут узла | По умолчанию 15 секунд, настройка 1–15 секунд | 8 секунд; QUIC 12 секунд |
| Общая длительность | Ручные запросы имеют индивидуальные таймауты | Пул sing-box ограничен 180 секундами; Flutter ждёт до 200 секунд |

Для 100 недоступных QUIC-узлов при одинаковой длительности каждого запроса простая оценка Naga — `ceil(100/8) × 12 = 156 секунд`, без подготовки движка и накладных расходов. Это расчёт по лимитам, не измерение сети.

## Локальное воспроизведение

Проверен настоящий `RuntimeController.probeWithRuntime` через временный Go overlay, с искусственным runtime: 8 быстрых узлов и 1 узел, удерживаемый управляемым барьером.

- Первый ответ готов через **27 мс**.
- После завершения 8 быстрых узлов в `ProbeSnapshot` всё ещё **0 результатов**.
- После освобождения медленного узла опубликованы все **9 результатов**; общая длительность **278 мс**.
- Наблюдавшийся максимальный параллелизм — **8**.

[Локальный журнал](testing/audit/20261013T174635Z-fixes/checks/karing-latency-proof-1.log).
Барьер специально удерживался 250 мс. Это демонстрация задержки публикации в нашем коде; она не измеряет скорость серверов или бинарного Karing.

## Дополнительные задержки Naga

1. При отключённом VPN проверка собирает конфигурацию, подготавливает правила и AWG-sidecars, запускает временный sing-box, проверяет узлы и останавливает движок. Karing в прочитанной ветке ручного теста требует уже запущенную службу.
2. [AWG-sidecars](../core/control/runtime_awg.go) при idle-проверке запускаются последовательно, с ожиданием готовности до 12 секунд для каждого. Это происходит до запуска общего пула узлов.
3. [olcRTC](../core/control/olc_probe.go) проверяется после sing-box, последовательно. Для каждого варианта запускается процесс, ожидается готовность до 20 секунд, затем выполняются два HTTP-замера с отдельным бюджетом до 24 секунд. Общий 180-секундный бюджет пула эту стадию не охватывает.
4. Обычный Linux `ProbeOnce` уже выполняет один запрос к Clash API. Однако [Android bridgeRuntime](../core/control/runtime_bridge.go) не передаёт интерфейс ProbeOnce: проверка списка попадает в Probe с двумя запросами. Это отдельная причина дополнительной работы на Android TUN.
5. Комментарий нашего `connectivityProbeURL` обещает HTTP без TLS. Но [используемый sing-box](https://github.com/SagerNet/sing-box/blob/56f91dfeabd6f4edbd437dfcc1e5b0ebc856b778/experimental/clashapi/proxies.go#L211) сбрасывает `http://` URL в Clash delay API и использует HTTPS по умолчанию. Поэтому фактическая метрика включает больше, чем обещает комментарий. Само по себе это не объясняет превосходство Karing: его стандартный URL тоже HTTPS.

## Порядок исправления

1. Публиковать результат каждого узла сразу. Завести прогресс задания и отдавать его клиенту через polling или поток; UI обновляет строки по ходу проверки.
2. Ограничить задания идентификатором/поколением, добавить отмену и защиту от поздних результатов старой проверки. Асинхронная задача должна владеть своим context: context завершившегося POST для неё не подходит.
3. Сделать параллелизм настраиваемым по платформе. Проверить 8/16/20 на ПК и 8/10 на мобильных; выбрать предел по времени, CPU, FD и влиянию на активный VPN.
4. Отделить быстрый список sing-box от подготовки AWG и olcRTC. Показывать независимый прогресс этих стадий; применить общий бюджет к полному заданию.
5. При параллельном olcRTC назначать каждому процессу отдельные конфигурацию и SOCKS-порт. Увеличение числа процессов на общем 10808 создаст конфликт.
6. Сохранить ProbeOnce через Android-обёртку. Двойной прогрев при выборе рабочего VPN-узла оценивать отдельно от ручной проверки списка.
7. Для idle-проверки готовить минимальную конфигурацию нужных outbounds, DNS и detours. Проверка не должна ждать ненужных правил маршрутизации; зависимости цепочек и DNS должны сохраниться.
8. Провести одинаковый прогон Naga/Karing: те же узлы, контрольный URL, режим VPN и состояние прогрева. Отдельно измерить время первого результата, время всех результатов, число таймаутов, нагрузку и фактическую задержку каждого узла. Для метрики зафиксировать реальный HTTP/HTTPS URL.

Первоочередная цель — быстрые результаты видны во время общей проверки, а недоступные узлы и отдельные транспорты не задерживают весь экран. Численное ускорение реального списка устанавливается сравнительным прогоном.
