# План исправлений и углублённого поиска ошибок Naga Network

Текущее выполнение и оставшиеся проверки: [FIX_AND_SECURITY_PROGRESS.md](FIX_AND_SECURITY_PROGRESS.md). Исходные checkbox ниже не заменяют поэтапный реестр результатов.

Версия 1, 2026-10-13. Основание: [отчёт](CODE_REVIEW_REPORT.md), [реестр выполнения ревью](CODE_REVIEW_PROGRESS.md), [первоначальный план](CODE_REVIEW_PLAN.md). Снимок предыдущего ревью — `2fe0f50043bdafe8cc59ee0e9a673f1a4ede31de` плюс зафиксированное рабочее дерево.

Цель: исправить известные причины, проверить обходы и связанные последствия, затем закрыть недоступные платформенные проверки. План подготовлен; его реализация этим документом не заявляется. Исходный реестр содержит 17 F-находок, D01–D05 по зависимостям/контрактам/поставке и H01–H04, требующие дальнейших доказательств. Новые поисковые направления ниже не являются новыми подтверждёнными уязвимостями.

## 1. Порядок работы

1. Сохранить воспроизводимую базу и regression proofs; подготовить исправленный compiler в отдельной среде.
2. Разблокировать Windows compilation и сразу поставить CI guard.
3. Закрыть границы файлов и elevated IPC, ownership rule sets и отмену запуска.
4. Исправить Android bridge/installer, desktop proxy/UI и iOS packaging.
5. Исправить парсеры/interval/original bytes и стоимость больших подписок.
6. Проверить actual dependencies/артефакты и включить release gates.
7. На подготовленных стендах подтвердить сетевое поведение и безопасность native операций.
8. Повторить поиск обходов/соседних причин; рефакторить крупные модули после поведенческих регрессий.

Зависимости блоков указывают условия их завершения; независимые подшаги могут начинаться раньше. R02/R04/R09 доступны после R00; кодовое исправление R03 можно готовить после R00, его Windows acceptance — после R01. Runtime R05 необходим полной проверке R06/R08. Поиск B00–B11 начинается сразу после фиксации базы и сопровождает каждое исправление. Серьёзный patch не ждёт завершения всего поиска: старое воспроизведение сохраняется в отдельной копии. Внутри блока отдельные дефекты исправлять отдельными обозримыми changesets, начиная с P1; отсутствие устройства не задерживает доступную component часть. R13 — итоговая матрица; отдельный native тест запускается, как только готов его артефакт и стенд, без ожидания всех остальных платформ.

## 2. Что считать исправленным

Для каждой карточки записывать корневую причину, затронутые пути и версии, минимальное изменение, совместимость/миграцию, regression до/после, поисковые варианты и результат на нужной платформе. Исправление и глубина доказательств учитываются раздельно.

| Статус исправления | Значение |
|---|---|
| OPEN | Есть находка/гипотеза; исправления нет |
| REPRODUCED | Дефект воспроизведён на указанном снимке/стенде |
| PATCHED | Код изменён; релевантные проверки ещё не завершены |
| PATCHED_PENDING_PLATFORM | Component проверки прошли, требуемая native проверка недоступна |
| VERIFIED | Исходный дефект и соседние варианты проверены после patch |
| CLOSED | Выполнены критерии карточки и проверены применимые последствия; остались только явно отдельные задачи |

| Уровень доказательства | Что он даёт |
|---|---|
| E0 — гипотеза | Есть предполагаемый путь, доказательства нет |
| E1 — код/контракт | Причина прослежена; реальная достижимость может быть неизвестна |
| E2 — component proof | Минимальный тест воспроизводит отклонение; ОС/привилегии могут быть подменены |
| E3 — native execution | Проверены реальная ОС, token/ACL, resources и operation |
| E4 — end-to-end/artifact | Проверен конкретный установленный build и наблюдаемое последствие по полной цепи |

P0–P3 отражает влияние и доступность, E0–E4 — доказанность. F17 сейчас подтверждён по коду, а фактический доступ medium клиента и privileged write требуют Windows VM. F08 требует device confirmation; F03 — проверки общего proof на Android; F05 — Windows reparse; F11 воспроизведён на synthetic Mach-O, наличие такого layout в поставляемом extension не установлено. Зелёный host тест не закрывает эти ограничения.

## 3. Работы по исправлению

### R00. Зафиксировать основу и перенести доказательства в регрессии

Находки: **подготовка/сквозные требования**. Зависимости: **нет**.

- [ ] **R00.01.** Сверить HEAD и рабочее дерево с baseline предыдущего ревью. Новые изменения сохранить отдельным снимком; прежние доказательства не переносить на новый код автоматически.
- [ ] **R00.02.** Сохранить неизменённую копию с дефектами. Из proofs/go и proofs/flutter перенести минимальные проверки в штатные test directories вместе с соответствующими исправлениями; убрать привязку к /tmp и машине автора.
- [ ] **R00.03.** Проверить собственные тесты: fixture действительно доходит до проблемной ветви, FAIL имеет ожидаемую причину, корректный вариант проходит. Для concurrency применять управляемые channels/barriers вместо зависимости только от коротких sleeps.
- [ ] **R00.04.** Зафиксировать compiler/SDK/engine fingerprints. Выбрать исправленный поддерживаемый Go toolchain по актуальным advisory и подготовить его в отдельном окружении; сохранить старую среду для воспроизведения. Нестандартная строка версии должна разбираться явно либо завершать scanner check понятной ошибкой.
- [ ] **R00.05.** Завести реестр исправлений и поисковых гипотез: снимок, affected platform, субъект/права, доказательство, причина, задача исправления, критерий приёмки и ограничения.

**Приёмка:** Каждая из F01–F17 имеет задачу, исходное доказательство и проверку будущего исправления. Исходные пользовательские изменения сохранены; старые и новые результаты различимы.

### R01. Разблокировать Windows-сборку и поставить ранний CI контроль

Находки: **F07**. Зависимости: **R00**.

- [ ] **R01.01.** Исправить сравнение результата WaitForSingleObject с WAIT_TIMEOUT с согласованием типов; проверить также остальные wait/timeout branches, а не только найденную строку.
- [ ] **R01.02.** Скомпилировать все Windows Go packages и tests. На Linux compile-only явно помечать как compilation; dummy executor не считать запуском тестов.
- [ ] **R01.03.** Добавить Windows compilation в обычный push/PR CI, включая naga-update, launcher, helper и hosts. Учитывать доступную модель fork PR и отсутствие signing secrets.
- [ ] **R01.04.** На Windows job выполнить применимые unit tests и собрать portable/setup. Реальную установку, повышение прав и маршруты выполнять на выделенной VM по R13.

**Приёмка:** Новый updater собирается; проверка CI воспроизводит прежнюю ошибку на старом снимке и проходит на исправленном. Timeout не выдаётся за успешное завершение процесса.

### R02. Защитить скачивание, распаковку и замену файлов обновления

Находки: **F02, F05**. Зависимости: **R00**.

- [ ] **R02.01.** Заменить предсказуемый каталог timestamp на новый приватный staging со случайным именем. Проверить права самого каталога и его родителей на каждой платформе; не переиспользовать чужой существующий staging.
- [ ] **R02.02.** Обеспечить безопасное создание и использование файлов. Проверка пути перед обычным open не защищает от замены между проверкой и открытием: применять платформенные операции с надёжным containment/handles, либо доказанно защищённый staging. Модель другого UID и процесса того же пользователя учитывать отдельно.
- [ ] **R02.03.** Проверять целостность того артефакта, который реально устанавливается. Проследить цепь download → verify → extract → replace: закрытие handle и повторное открытие по имени не должны позволять установить непроверенные байты.
- [ ] **R02.04.** Распаковывать архив сначала в новый staging. Проверять ../, абсолютные/drive/UNC пути, ссылки, junction/reparse, alternate streams, дубликаты имён и коллизии после нормализации; задать пределы числа файлов, фактических распакованных байтов и времени. Выбор файловых API зависит от исправленного toolchain R00, включая Windows junction advisory.
- [ ] **R02.05.** Сделать замену набора UI/control/engines восстанавливаемой: предыдущая версия, точки отказа, проверка комплектности, cleanup, restart и version skew. Нельзя обещать атомарность всего дерева только из-за rename одного файла.
- [ ] **R02.06.** Внедрить сбои на каждой границе: обрыв download, digest mismatch, занятый файл, отказ replace, crash/restart. Внешний тестовый файл должен остаться неизменным; при неудаче доступна согласованная старая установка.

**Приёмка:** F02/F05 regression PASS; обход через замену пути и Windows reparse не подтверждается на соответствующем стенде. Успешное обновление и возврат старой версии проверены отдельно.

### R03. Сузить полномочия Windows helper и проверить путь до повышения прав

Находки: **F17**. Зависимости: **R00, R01**.

- [ ] **R03.01.** Проследить medium-token клиент → helper pipe → spawn elevated host → host request → операции с файлами/процессами. Установить реальные DACL/MIC, SID, install location и elevation: чтение кода ещё не доказывает, что произвольный клиент добирается до операции.
- [ ] **R03.02.** Убрать произвольный LogPath из запроса либо генерировать его только внутри host в доверенном каталоге. Проверять родителей/reparse; не полагаться на startsWith, filepath.Clean или одну проверку «лежит рядом с exe».
- [ ] **R03.03.** Перечислить и ограничить остальные поля: BinaryPath, ConfigPath, Env, pipe names, command modes, cwd, inherited handles, arguments. Helper должен предоставлять конкретную операцию VPN, а не универсальные права на файл/процесс.
- [ ] **R03.04.** Определить авторизацию IPC и bounded protocol: размер сообщения, deadlines, закрытие peer, недопустимые команды и flood. Проверка PID/имени exe сама по себе не является достаточной авторизацией; отдельно оценить возможности процесса того же SID.
- [ ] **R03.05.** В Windows VM после R01 проверить разрешённый клиент, сторонний medium-token процесс того же SID, другой пользователь, reparse parent и защищённый тестовый файл. Для возможной подмены binary использовать безвредный test executable; зафиксировать фактический уровень token.

**Приёмка:** Host больше не открывает управляемый клиентом произвольный путь. Реальная проверка Windows разграничивает устранённый дефект и недоказанные способы повышения прав; до неё статус PATCHED_PENDING_PLATFORM.

### R04. Исправить весь жизненный цикл rule sets и обновление кеша

Находки: **F01, F15**. Зависимости: **R00**.

- [ ] **R04.01.** Выбрать единого владельца paths/Stats и результатов workers. Проверить все чтения/записи: main loop с cache hits и errors, worker completion, timeout/cancel и возврат. Один mutex только вокруг финального ApplyLocal недостаточен.
- [ ] **R04.02.** Передавать caller неизменяемый результат. Late worker не должен менять возвращённые данные; при отмене он должен завершаться без блокировки на отправке результата. Определить владельца background fetch, если он сохраняется, и его deadline.
- [ ] **R04.03.** Ограничить одновременные fetch и объединять одинаковые URL в пределах выбранной политики. Проверить concurrent Materialize, атомарность cache replacement, разные форматы и недопустимый payload.
- [ ] **R04.04.** Сохранить metadata загрузки и interval, учитывать истечение, clock changes и старый cache без metadata. Обновлять просроченный cache; временная ошибка fetch не должна без объяснения лишать пользователя пригодных правил.
- [ ] **R04.05.** Проверить retry/fallback в runtime_ruleset.go с настоящим config check поддерживаемых engine versions. Фиксировать, какие правила фактически применились, а не считать любой успешный restart эквивалентным исходной policy.
- [ ] **R04.06.** Выполнить race на mixed cache hit/miss, late success/error, timeout, cancellation, повторном refresh и нескольких simultaneous callers. Проверить стабильный snapshot и отсутствие роста workers.

**Приёмка:** F01/F15 regression PASS. После возврата результат не меняется; просроченные правила обновляются, а failures имеют заданный и видимый исход.

### R05. Сделать остановку доступной на любой стадии запуска

Находки: **F16**. Зависимости: **R00**.

- [ ] **R05.01.** Описать Start/Stop/Select/Refresh/Policy/Reconnect как операции с владельцем ресурсов и поколением сессии. Составить порядок locks Server/Controller/Store/bridge; определить, где допустимы длительные внешние вызовы.
- [ ] **R05.02.** Выделить cancellation path, доступный независимо от занятого mutation lock. Простое исключение stop из одного mutex не закрывает проблему, если controller lock всё ещё удерживается при блокирующей операции.
- [ ] **R05.03.** Передать отмену через load/preflight/ruleset/sidecar/engine/readiness/probe/configure. Устаревший Start/reconnect/callback не должен включить VPN заново после принятого Stop.
- [ ] **R05.04.** Сохранить согласованность mutations и текущего API; если контракт меняется, совместно обновить Dart/Swift DTO и fixtures. Различать запрос остановки, завершённый cleanup и ошибку restore.
- [ ] **R05.05.** Проверить HTTP Start–Stop, Stop–Stop, Stop–policy reconnect, cancellation до/после acquire и caller disconnect. Измерить принятие отмены и завершение cleanup отдельно; бюджеты привязать к стадиям и реальным внешним timeouts.

**Приёмка:** F16 regression PASS на HTTP boundary. Stop не ждёт окончания probe для начала отмены; после него старое поколение не возвращает connected и не оставляет ресурсы.

### R06. Исправить Android bridge, TUN ownership и готовность сервиса

Находки: **F03**. Зависимости: **R00, R05**.

- [ ] **R06.01.** Назначить ровно одного владельца ожидания child exit. Разобрать normal Stop, early/late exit, Kill failure, revoke и повторный Start; исключить двойной Wait и удержание общего lock при взаимозависимом callback.
- [ ] **R06.02.** Привязать hev, FD и события к поколению сессии. Поздний exit старого процесса не должен закрыть FD нового VPN; child failure должен инициировать согласованное завершение bridge/runtime/VpnService.
- [ ] **R06.03.** Добавить наблюдаемую готовность VpnService/TUN и handshake с native runtime. Подтвердить либо опровергнуть H02: сейчас channel подтверждает запуск сервиса раньше готовности FD.
- [ ] **R06.04.** Не считать живой SOCKS/sing-box достаточным доказательством Android datapath. Определить, как bridge failure меняет runtime status и какие условия позволяют безопасный recovery.
- [ ] **R06.05.** На host воспроизвести exit/Stop/replacement races; на Android — consent/revoke/recreate, process death, новый FD, background и переключение движка. Packet capture должен отделить заблокированный трафик от возможного выхода вне туннеля.

**Приёмка:** F03 regression PASS; FD/process освобождаются ровно один раз. На устройстве после bridge failure состояние UI/runtime соответствует фактическому пути трафика. H02 имеет отдельный результат.

### R08. Исправить режим прокси, сохранение настроек и достоверность UI

Находки: **F12, F04, F06**. Зависимости: **R00, R05**.

- [ ] **R08.01.** Формировать ровно один канонический loopback listener system proxy. Проверить reserved tag, duplicates, route references, смену TUN/proxy и двукратное применение transform; persisted original не изменять.
- [ ] **R08.02.** Проверить настоящий bind/readiness перед применением настроек ОС; занятый port и неработающий listener должны давать явный отказ с восстановлением прежних настроек.
- [ ] **R08.03.** Сравнивать точный host/port и устанавливаемый набор настроек. Исправить proxyPointsAt и проверить соседний clearStuckOlcProxy. Порт сам по себе не доказывает, что настройки принадлежат Naga.
- [ ] **R08.04.** Restore должен сохранять изменения пользователя, сделанные во время VPN. Разобрать частичный gsettings/registry failure и rollback по ключам; нельзя безусловно восстанавливать весь snapshot поверх новых пользовательских значений.

### R09. Сделать iOS упаковку однозначной и убрать опасное изменение бинарника

Находки: **F09, F11**. Зависимости: **R00**.

- [ ] **R09.01.** Отделить compile, link, patch при необходимости, sign и package. Неуспешная компиляция должна завершать сборку ошибкой; наличие старого .app/IPA не является разрешением продолжить.

## 5. B00 — как «раскручивать» каждую ошибку

Для каждой F-находки и новой гипотезы выполнять одну и ту же последовательность. Цель — установить максимальное подтверждённое последствие и область той же причины.

- [ ] **B00.01. Источник и путь.** Найти, кто контролирует вход: удалённый provider, импортирующий пользователь, браузер, другой UID, процесс того же SID, builder. Проследить данные до опасной операции и перечислить проверки по дороге.
- [ ] **B00.02. Достижимость.** Доказать каждое обязательное условие: формат принят, route авторизован, ветвь активна, callback доставлен, peer допущен, операция идёт нужными правами. Проверить реальный режим установки/платформу, а не только abstract code path.
- [ ] **B00.03. Минимальное доказательство.** Подготовить fixture и ожидаемое внешнее свойство. Использовать управляемый test server/process и отдельные test files; фиксировать observed failure, состояние и effective rights. Подготовка стенда не должна зависеть от настоящих профилей/ключей.
- [ ] **B00.04. Предел последствия.** Начать с непосредственного эффекта: неверный ответ, hang, resource leak, чтение/запись файла, crash. Отдельно проверять следующий переход — доступ к секрету, изменение executable, выполнение с повышенными правами. Отрицательный результат тоже сохранять.
- [ ] **B00.05. Соседние пути.** Искать ту же опасную операцию/ownership pattern в другом движке, платформе, download fallback, helper, installer, recovery, delete/refresh и аварийном cleanup. Результат поиска — конкретный список call sites с исходом по каждому.
- [ ] **B00.06. Цепочка.** Соединять несколько ошибок только при совместимых предпосылках: один субъект, нужный порядок и сохраняющееся состояние. Каждый переход должен иметь доказательство; «если когда-нибудь получится ещё X» остаётся отдельной гипотезой.
- [ ] **B00.07. Обход исправления.** После patch повторить старый proof, изменить кодировку/alias/parent path/timing/поколение/platform и проверить fallback. Исправление проверяется по внешнему свойству, не только по появлению if/mutex.
- [ ] **B00.08. Решение.** Обновить влияние, confidence, affected versions, dedup и задачу. Неподтверждённую цепочку оставить UNVERIFIED с конкретным недостающим условием; опровергнутую гипотезу закрыть только в пределах проверенного класса входов.

Шаблон карточки: `вход → проверки → опасная операция → непосредственное последствие → следующий доказанный переход`. Приложить snapshot/build hash, steps/fixture, expected/actual, роли/права, evidence, фикс и regression. Для rejected/unverified записывать причину и способ дальнейшей проверки.

## 7. Кампании поиска по классу причин

### B01. Файловые границы, обновление и сохранение данных

## 8. Бюджет проверки и артефакты

Порядок одной задачи: минимальный исходный FAIL → fix → релевантный regression → соседние варианты → затронутые platform/native checks. Общую suite повторять после связанного набора изменений, а не после каждого документа. Не менять goldens/fixtures ради зелёного результата без объяснённого изменения поведения.

Fuzz: первоначально 60 секунд на новую/затронутую цель, затем более долгий отдельный job для покрываемых classes и новых seeds. Увеличивать бюджет при новых counters/crashes/неизученной ветви; длительность сама по себе не закрывает риск. Планировать CPU/time/memory пределы. Для concurrency использовать контролируемые расписания плюс race; для native memory — поддерживаемые sanitizers, отдельно от Go race.

Performance: сохранить старое измерение, после fix провести одинаковые inputs и несколько повторов. Вывести regression threshold из новой базы и поддерживаемой нагрузки; не назначать произвольный SLA всем платформам. Native leak/resource stress и UI responsiveness измерять на соответствующем стенде.

Для каждого run сохранять: commit + рабочий diff + hashes, toolchain/OS/device и build hash, точные argv/env overrides, фикстуры, expected/actual, exit codes, packet/resource traces и пределы доказательства. Обычный тест на старой базе не должен незаметно подхватить уже исправленный файл. В evidence не сохранять реальные профили/секреты; это относится к качеству воспроизводимого стенда, а не ограничивает исследование собственных компонентов.

Материалы новой реализации держать в `docs/testing/audit/<new-run-id>/`; исходные `20261013T100903Z-full-review` сохранять неизменными как evidence дефектов. Минимальные regression tests/corpus и итоговый отчёт о fixes должны быть доступны в репозитории; подробные local traces — отдельно. Состояние прежнего ревью не переписывать так, будто дефекты уже были исправлены при исходной проверке.

## 9. Критерии завершения и проверка логики плана

- Все F01–F17 имеют ровно одного владельца этапа исправления и проверку корневой причины; D01–D05 и H01–H04 распределены отдельно.
- Для каждого существенного нового последствия есть отдельное доказательство достижимости и прав; исходные условия разных субъектов не смешаны в одну «атаку».
- Release gates проверяют actual артефакты и завершаются ошибкой при реальном нарушении; advisory/stand gaps видимы, compile-only не выдаётся за execution.
- File integrity, original/migrated profile semantics, Stop terminal state и восстановление внешних настроек проверены после fixes.
- Оставшиеся native gaps отражены как PATCHED_PENDING_PLATFORM/UNVERIFIED с необходимым стендом. Отсутствие полного iOS VPN не превращается в обещание его реализации этим планом.
- Рефакторинг не является условием срочных security patches. Поведенческие ошибки закрываются раньше широкого изменения структуры.
- R00 создаёт основу; R01 раннюю Windows compilation; R04 предшествует усложнению rule-set refresh; R05 необходим полноценным cancellation/lifecycle сценариям. Исправленный toolchain подготавливается раньше выбора новых файловых containment API.
- Глобальная итоговая зависимость R13 не запрещает ранние native proof. B00–B11 начинаются после R00 и сопровождают patches; R14 сверяет их результаты в конце. Дополнительный рефакторинг не включён в зависимости срочных fixes.
- «Закрыть все гипотезы» не означает гарантированно найти все возможные уязвимости: достаточный итог — доказанная причина/проверенный класс входов либо конкретно обозначенная неопределённость.

План проверяется на полноту F-ID, уникальность task-ID, отсутствие циклов зависимостей, сохранение исходников и корректность ссылок. Проверка структуры плана не заменяет выполнение его steps.
